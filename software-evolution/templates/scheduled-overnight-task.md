# Scheduled Overnight Task Prompt

Use `$software-evolution overnight` on the configured local project.

Work autonomously from `effective_config` and repository rules. If the governance control plane is missing, initialize it and continue in the same run. Prefer an isolated worktree. Maintain a stable parent Run scope and a candidate portfolio across user/business outcomes, engineering/reliability, and architecture/evolution. Repeatedly discover, prove, prioritize globally, repair, test, browser/runtime verify when applicable, re-scan, update changed engineering memory, and checkpoint safe R1/R2 batches while the host remains available and safe verifiable work exists.

Do not stop because of file, finding, cycle, checkpoint, or repair-batch counts. Record those values as telemetry only. A coherent repair may touch many files when its behavior, callers, rollback, and verification are known.

Do not wait for routine confirmation. Record decision-, specialist-, environment-, or approval-blocked items and continue independent safe work. Never deploy, mutate production/shared data, change permissions/credentials/alerts/flags, publish remotely, rewrite Git history, or perform R3/R4 contract/model changes without separate exact authorization.

Do not declare completion because one defect family is exhausted. Before completing, run an outside-cluster counterexample scan, reconcile open debt/findings/capabilities/rules/critical journeys, obtain browser evidence or an exact blocker for runnable UI, update schema-v3 coverage metadata, and require `validate_run_completion.py` to return `OK`. End with the `RUN-*` ledger, three-lane coverage, exact tests/runtime results, reused evidence fingerprints, remaining risks, and the real stop reason. Use explicit `$software-evolution resume <id>` only for host interruption, drift, ambiguity, or targeted recovery; ordinary batch checkpoints continue automatically.
